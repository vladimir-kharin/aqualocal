## Суть

Сейчас непонятно, что именно работает неправильно: лог фиксирует факты («распознано», «отправлено»),
но не времена и не параметры работы. Первый симптом — **распознавание кажется долгим, как будто идёт
на процессоре, а не на видеокарте**. Из лога это ни подтвердить, ни опровергнуть.

Задача из двух частей: (1) довести логирование до уровня, на котором такие вопросы закрываются одной
строкой лога; (2) на этих данных разобрать конкретный случай с медленным распознаванием.

## Проверенные факты (2026-08-13)

Замер по 39 запросам к локальному STT-серверу из `aqualocal.log` за 11–13 августа:

- отношение «секунд аудио на секунду работы» (RTF): **мин 2.5×, медиана 8.4×, макс 13.5×**;
- короткая фраза (2–6 с) — 0.8–2.1 с ожидания; длинная (40–90 с) — 4–10 с;
- ошибок транскрибации и сбоев звукового устройства — **0**;
- загрузок модели 6, все успешные, но **9 срабатываний сторожа** «модель грузится дольше 30 с».

Окружение: RTX 3060 **12 ГБ** (в README упомянута 3090 — это машина автора апстрима), драйвер 561.09,
`ctranslate2` 4.5.0, CUDA-типы доступны, включая `float16`. На момент проверки **занято 10.8 из 12 ГБ**
видеопамяти посторонними процессами (браузеры, Teams, Electron, mstsc).

**Промежуточный вывод:** модель работает на GPU (на CPU RTF был бы 0.3–1×, то есть минутная фраза
считалась бы минутами). Ощущение «долго» складывается из трёх других причин: распознавание стартует
только после отпускания клавиши и обрабатывает фразу целиком; есть фиксированный оверхед ~1 с;
скорость плавает в 5 раз — вероятнее всего из-за нехватки свободной VRAM и вытеснения памяти в
системную. Подробности — `docs/kb/Производительность_распознавания_на_GPU.md`.

## Чего не хватает в логе (это и есть объём работы)

1. **Время распознавания для микрофонных режимов.** Сейчас пишется только длина аудио (`app.py:458`);
   длительность есть исключительно у запросов STT-сервера (`app.py:356`).
2. **Разбивка задержки по стадиям**: склейка буферов → VAD → `transcribe` → доставка (вставка в курсор /
   HTTP в Singularity / запись файла). Сегодня 4 секунды ожидания неразличимы: это модель или сеть.
3. **Строка «паспорт запуска»** сразу после загрузки модели: `device`, `compute_type`, `MODEL_SIZE`,
   версия ctranslate2, имя GPU, всего/свободно VRAM, время загрузки модели в секундах.
   Она закрывает вопрос «а не на CPU ли оно» навсегда.
4. **Замер VRAM перед каждым распознаванием** (или хотя бы при заметном превышении обычного времени) —
   чтобы связать просадку скорости с занятой памятью.
5. **Ротация файла** — сейчас `aqualocal.log` растёт неограниченно, `RotatingFileHandler` не подключён.
6. **Уровень логирования из `.env`** (`LOG_LEVEL=INFO|DEBUG`) — сейчас `DEBUG` включается правкой кода.
7. Единый префикс события и идентификатор фрагмента, чтобы строки одного распознавания можно было
   собрать вместе (`[stt#42] …`).

## План

1. Ввести `LOG_LEVEL` и ротацию (`RotatingFileHandler`, ~2 МБ × 3 файла) — `app.py:14-20`.
2. Добавить «паспорт запуска» после успешной загрузки модели — `app.py:405-409`.
3. Обернуть стадии `process_audio` замерами и писать одну итоговую строку с разбивкой —
   `app.py:431-472`; ту же разбивку дать серверному пути (`app.py:338-361`).
4. Собрать замеры за несколько дней обычной работы, сверить RTF при свободной и занятой VRAM.
5. По результатам решить, нужно ли что-то из кандидатов на ускорение (`compute_type="int8_float16"`,
   модель поменьше, прогрев после загрузки, потоковое распознавание) — и завести отдельную задачу.

## Открытые вопросы

- Писать ли времена в отдельный машинно-читаемый файл (`metrics.jsonl`) в дополнение к текстовому логу —
  удобнее считать статистику, но это второй артефакт.
- Нужны ли данные о VRAM через `pynvml` (лишняя зависимость) или достаточно разового вызова
  `nvidia-smi` при старте.
