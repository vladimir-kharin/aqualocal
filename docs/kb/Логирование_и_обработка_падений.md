# Логирование и обработка падений

## Как устроено сейчас

Единственный приёмник — файл `aqualocal.log` рядом с `app.py`, уровень `INFO`, формат
`%(asctime)s - %(levelname)s - %(message)s`, кодировка UTF-8 (`app.py:14-20`). Настраивается
**первым делом**, до любых импортов — чтобы падение на импорте тоже попало в файл. Файл в `.gitignore`.

Три уровня перехвата падений, все три поставлены из-за `pythonw.exe` (у него нет stderr, ошибка
иначе исчезает бесследно — см. [[Окружение_запуск_и_venv]]):

1. `sys.excepthook` → `handle_exception` (`app.py:24-31`) — падения главного потока;
2. `threading.excepthook` → `handle_thread_exception` (`app.py:101-109`) — падения рабочих потоков,
   которые `sys.excepthook` **не** покрывает; без него смерть `stt_worker` выглядела бы как тишина
   в логе при живом трее;
3. локальные `try/except` вокруг каждого внешнего действия (трей, оверлей, запись в Obsidian,
   отправка в API) — с `exc_info=True` там, где нужен трейсбек.

Отдельно — **watchdog загрузки модели** (`app.py:393-402`): `WhisperModel(...)` это нативный вызов,
он может не упасть, а зависнуть (например, если VRAM занята). Сторож каждые 30 с пишет в лог,
сколько уже ждём, и советует посмотреть `nvidia-smi`.

## Что пишется по факту

- стадии запуска: мьютекс, пути NVIDIA, подключение `singularity.sender` и `obsidian.writer`,
  загрузка модели, открытие `InputStream`, создание трея и оверлея;
- каждое распознавание с микрофона: `[<режим>] Распознано (<N> сек аудио): <текст>` (`app.py:458`);
- каждый запрос к локальному серверу: `[stt] <N> сек аудио за <M> с: <текст>` (`app.py:356`) —
  **единственное место, где логируется длительность распознавания**;
- отбраковка по VAD, ошибки транскрибации, сбои звукового устройства, результаты отправки в API
  и записи в Obsidian, работа offline-очередей.

## Чего в логе нет (и это мешает диагностике)

- **времени распознавания для микрофонных режимов** — есть только длина аудио. Замерить скорость
  можно лишь по строкам `[stt]` (то есть по чужим запросам к серверу), а не по своим горячим клавишам;
- разбивки задержки на стадии: склейка → VAD → `transcribe` → доставка (вставка в курсор, HTTP,
  запись в файл). Сейчас 4 секунды ожидания неразличимы: это модель или сеть Singularity;
- **фактических параметров запуска модели**: `device`, `compute_type`, версия ctranslate2, имя GPU,
  свободная VRAM. Ушла ли модель на CPU по тихому фолбэку — из лога не видно;
- времени загрузки модели (есть только предупреждения сторожа при превышении 30 с);
- **ротации**: файл растёт неограниченно (на 2026-08-13 — 63 КБ; `RotatingFileHandler` не подключён);
- уровня логирования в `.env`: `DEBUG` включается только правкой кода.

Это и есть содержание задачи `docs/tasks/ПодробноеЛогирование/`.

## Приёмы чтения лога

```powershell
Get-Content aqualocal.log -Tail 50 -Wait                    # смотреть вживую
Select-String -Path aqualocal.log -Pattern '\[stt\]|Распознано'   # только распознавания
Select-String -Path aqualocal.log -Pattern 'КРИТИЧЕСКАЯ|ERROR'    # падения
```

Осмысленная выжимка производительности из тех же строк — в [[Производительность_распознавания_на_GPU]].
