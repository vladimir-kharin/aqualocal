# Архитектура: один процесс, три потока, обмен через очереди и флаги

Всё приложение — **один процесс** `pythonw.exe app.py`. Второй копии не бывает: на старте берётся
именованный мьютекс Windows `AquaLocal_STT_Mutex_v1`, при `ERROR_ALREADY_EXISTS` (183) копия молча
выходит (`app.py:36-50`).

## Потоки

| Поток | Что делает | Где создаётся |
|---|---|---|
| **главный** | Tkinter `mainloop()` — оверлей записи, перерисовка ~30 fps | `app.py:720-727` |
| **`stt_worker`** | грузит модель, слушает хоткеи, пишет с микрофона, вызывает Whisper и обработчики режимов | `app.py:694` |
| **`stt_server`** | HTTP-сервер `POST /stt` для других программ на машине (если задан `STT_PORT`) | `app.py:380` |
| трей | `pystray.Icon.run_detached()` — свой фоновый поток внутри библиотеки | `app.py:715` |
| watchdog | одноразовый сторож: пишет в лог, если загрузка модели идёт дольше 30 с | `app.py:395-402` |
| PortAudio | callback `audio_callback` вызывается из потока звуковой библиотеки | `app.py:201` |

**Главный поток отдан Tkinter намеренно** — tkinter не переживает работу из чужого потока.
Поэтому вся полезная работа ушла в `stt_worker`, а UI получает данные только через очередь и флаги.

## Обмен состоянием

Никаких классов-контроллеров: обмен идёт через **модульные глобальные переменные** (`app.py:159-173`).

- `audio_queue` — куски `numpy`-массива от микрофонного callback к `process_audio`;
- `flash_queue` — сообщения-подтверждения из рабочего потока в UI (`flash(text, ok, sec)`);
- `is_recording`, `is_transcribing`, `current_mode`, `current_volume`, `transcribe_started` —
  флаги, которые оверлей опрашивает каждый кадр и по ним выбирает, что рисовать;
- `app_running` — общий стоп-флаг; выход из трея делает `os._exit(0)` (`app.py:685-690`);
- `model_lock` — единственный настоящий замок: сериализует `model.transcribe`, чтобы микрофон и
  HTTP-сервер не дрались за видеопамять (`app.py:173`, `app.py:419`).

Флаги пишутся из одного потока и читаются из другого без синхронизации. Это осознанно: значения
атомарны (bool/float), а UI переживает чтение слегка устаревшего значения. **При добавлении
составного состояния (словарь, список) так делать уже нельзя** — нужна очередь или замок.

## Путь звука (режим с микрофона)

1. `sd.InputStream` открыт постоянно, 16 кГц, моно, float32 — callback пишет в `audio_queue`
   **только пока `is_recording`** (`app.py:201-211`);
2. `stt_worker` в цикле опрашивает `keyboard.is_pressed(...)` по всем хоткеям; нажатие → чистка
   очереди → `is_recording = True` → ожидание отпускания (`app.py:480-505`);
3. отпускание → `process_audio(mode)`: склейка кусков, VAD, распознавание, обработчик режима
   (`app.py:431-472`);
4. весь `InputStream` обёрнут в бесконечный `while app_running` с перезапуском через 2 с — падение
   звукового устройства не убивает приложение (`app.py:475-509`).

Ключевое следствие архитектуры: **распознавание начинается только после отпускания клавиши**, весь
фрагмент уходит в модель разом. Отсюда ожидание, пропорциональное длине фразы — см.
[[Производительность_распознавания_на_GPU]].
