# Производительность распознавания: факты и методика проверки

## Замеренное (2026-08-13, `aqualocal.log`)

По строкам `[stt] <длина аудио> сек аудио за <время> с`, 39 запросов:

| Показатель | Значение |
|---|---|
| Отношение «секунд аудио на секунду работы» (RTF) | мин **2.5×**, медиана **8.4×**, макс **13.5×** |
| Короткая фраза (2–6 с аудио) | 0.8–2.1 с ожидания |
| Длинная фраза (40–90 с аудио) | 4–10 с ожидания |
| Ошибок транскрибации / сбоев звука | 0 / 0 |
| Загрузок модели | 6, все успешные, но **9 срабатываний сторожа** «грузится дольше 30 с» |

**Вывод: модель работает на GPU.** `large-v3` в FP16 на CPU даёт RTF около 0.3–1×, то есть
40-секундная фраза распознавалась бы минуты, а не 4–5 секунд. Ощущение «долго» имеет другую природу
(см. ниже). Разброс 2.5×–13.5× при одинаковой модели — отдельный симптом: скорость плавает.

## Откуда берётся ощущение «долго»

1. **Распознавание стартует только после отпускания клавиши** — весь фрагмент идёт в модель разом
   (`app.py:503`). При RTF 8× минута диктовки = ~7 секунд ожидания, и это ожидание видимое.
   Потоковое распознавание по ходу речи архитектурой не предусмотрено.
2. **Фиксированный оверхед ~0.8–1 с** даже на 2-секундной фразе: прогон VAD, подготовка входа,
   старт нативного вызова.
3. **Конкуренция за видеопамять.** На машине владельца GPU — RTX 3060 **12 ГБ**, и на момент проверки
   было занято **10.8 из 12 ГБ** другими процессами (браузеры, Teams, Electron, mstsc). Модель
   `large-v3` FP16 требует ~3 ГБ. При нехватке VRAM драйвер NVIDIA не отдаёт честную ошибку, а
   уводит память в системную (sysmem fallback) — скорость падает в разы, а внешне всё «работает».
   Косвенное подтверждение: сторож 9 раз фиксировал загрузку модели дольше 30 секунд.
4. Доставка результата тоже в общем времени: `insert_at_cursor` держит 150 мс на подмену буфера
   (`app.py:215-222`), режим задачи ходит в сеть до показа плашки.

## Как проверить, что распознавание на GPU

```powershell
.venv\Scripts\python.exe test_cuda.py     # список compute-типов CUDA; пусто => сборки без GPU
nvidia-smi                                 # свободная VRAM и кто её держит
nvidia-smi --query-gpu=memory.used,memory.total,utilization.gpu --format=csv -l 1   # во время диктовки
```

Признаки настоящего CPU-режима: `test_cuda.py` не печатает типы; в логе после «Загрузка модели»
идёт исключение про cuDNN/cublas; RTF падает ниже ~1×. Ни одного из них в текущем логе нет.

**Тихого фолбэка на CPU у faster-whisper не бывает** — `WhisperModel(device="cuda")` при недоступной
CUDA бросает исключение, которое ушло бы в лог как «Ошибка загрузки модели» (`app.py:410-414`).
Поэтому вопрос «а не на процессоре ли оно» закрывается одной строкой лога, если её туда добавить —
см. [[Логирование_и_обработка_падений]].

## Что можно ускорить (не сделано, кандидаты)

- освободить VRAM перед работой — самое дешёвое действие с наибольшим эффектом;
- `compute_type="int8_float16"` — вдвое меньше памяти, скорость выше, качество чуть ниже;
- модель поменьше (`large-v3-turbo`, `medium`) — константа `MODEL_SIZE`, `app.py:156`;
- `beam_size` уже равен 1 — минимальный (`app.py:421`), запас здесь исчерпан;
- потоковое распознавание кусками во время удержания клавиши — переделка `process_audio`;
- прогрев модели пустым прогоном после загрузки, чтобы первое реальное распознавание не платило
  за инициализацию ядер.
